1 Rationale (from Web Based)

The rationale of the mobile-based application is carried over from the web-based study, which established that conventional attendance consumes five to ten minutes of every class meeting, produces handwritten records that are difficult to read, aggregate and report, and cannot prevent proxy attendance. The web-based system answered those problems with QR codes and RFID, but it is accessed through a browser — a step that is awkward at exactly the moment attendance matters most: standing at the classroom door.

The mobile application therefore inherits the same problem statement and addresses the friction that remains after moving from paper to a browser. Three observations support taking the work to a phone.

First, students are mobile-first. Most enrolment, announcement and learning-management traffic in schools already reaches students on a phone rather than a desktop. A web page that must be typed into a mobile browser, found in history, signed into, and refreshed is a poor fit for the one to three seconds a student has while walking into a room. A native application keeps the session, the class list and the camera control together, so generating a QR pass or tapping a card reader becomes a single action.

Second, connectivity in classrooms is unreliable. Lecture rooms and corridors are the least predictable parts of a campus network. A browser session that drops mid-request leaves an ambiguous result — the student does not know whether the check-in was recorded. A mobile client can queue a check-in, retry it, and show a definite state to the student, while still writing the server's timestamp so the record remains consistent.

Third, a phone already carries the two capture devices the system needs. The camera handles QR codes; Bluetooth or camera scanning can pair the ESP32 reader without opening a laptop. A mobile app can also use device-local storage to remember the student's identity and recent passes, and can notify the student when a professor opens a session — a capability a plain web page cannot deliver reliably across mobile browsers.

The study therefore develops a mobile-based companion for the same attendance system: a phone application where students sign in, view their classes and schedules, generate their time-limited QR pass, scan the section enrolment code, and review attendance history — while the professor's web dashboard and the door-side ESP32 reader continue to share the same database. The rationale is not to replace the web system but to remove the last barrier between a student and an accurate attendance record.

Problem statement: a browser-based system still requires navigation, a live connection and a familiar user session at the classroom door; a mobile application is needed so a student can check in with one tap, tolerate weak connectivity, and be notified when attendance opens.

2 Blueprint (Mobile Based)

The mobile application is a thick client on the existing three-tier architecture: it replaces the browser as the presentation tier while sharing the same PHP logic and MySQL data. It does not own a separate database — one source of truth prevents the web and mobile records from diverging.

2.1 Mobile modules

Authentication

Same credential rules as the web; the server issues a revocable bearer token stored in secure storage, replacing the browser session cookie.

Class & schedule

Sections, meeting days and times read from the shared database, scoped to the signed-in student.

QR pass

Requested from the server when a session opens; rendered on device with a live countdown that matches the server expiry.

Enrolment

Camera scans the section QR shown on the professor's screen; the student ID is confirmed in the app.

Reader pairing

The professor may pair or revoke ESP32 readers from a phone without opening a laptop.

Offline resilience

Cached class list; a pending check-in is queued and retried, so the app always shows a definite state.

Notifications

Optional local/push notification when a session opens for an enrolled section.

History

Attendance records with date, method (QR/RFID) and status, filtered by academic term.

Design principle: validation stays on the server. The mobile app never decides attendance — it only presents a pass and sends a token. That keeps web, mobile and RFID check-ins under one set of rules (expiry, single use, section ownership, rate limiting).

4 Software Development Phases (Mobile Development)

The mobile application follows the same SDLC as the web study, with the platform-selection and device-testing steps expanded — a distinct sequence sometimes called the mobile application development life cycle.

Phase 1 — Requirements and Platform Selection

Collected the requirements carried over from the web study (role-based sign-in, class and schedule views, time-limited QR pass, enrolment by code, history) plus mobile-specific ones: camera permission flow, fast launch from a locked screen, low-data operation, offline display, and device storage for credentials. Compared Flutter, React Native and native Android against the school's skill set and the single-team constraint; Flutter was selected for one codebase and strong camera/QR packages.

Phase 2 — Architecture and API Contract

Defined the client–server split: the app presents and caches, the server validates and stores. Specified JSON endpoint schemas, bearer-token authentication with revocation, error codes for expired or duplicate passes, and the offline queue protocol (unique request ID so a retried check-in cannot create a duplicate row). Produced the system and activity diagrams for: student enrolment, QR check-in, and reader pairing.

Phase 3 — UI/UX Design

Converted the web blueprint into mobile screens: bottom navigation for Home / Classes / Attendance, a full-screen pass view with a live countdown, and a large camera frame for enrolment. Wireframes were produced first, then applied to Material widgets using the same blue palette, Lucide icons and typography as the web dashboard so the two interfaces read as one system.

Phase 4 — Core Implementation

Built in dependency order: splash and authentication (secure token storage), the dashboard with cached classes, the class list with schedules, and the profile. Every screen was wired to the REST endpoints and verified against the existing web database.

Phase 5 — Feature Integration

Added the QR pass renderer tied to server-issued expiry, the camera-based enrolment scanner, the offline queue with retry, professor-side reader management, and optional session notifications. Integrated the same conflict and validation rules already enforced by the web API rather than duplicating them.

Phase 6 — Testing

Executed unit tests for models and state, widget tests for screen behaviour, and integration tests against a staging API. Device-level testing covered the camera permission path, QR readability across screen brightness, weak/lost connectivity and retry, cold launch, and emulator plus physical handset on Android 8–14 (and iOS where supported). Usability testing asked students to perform a check-in and timed it against the browser flow.

Phase 7 — Packaging, Deployment and Maintenance

Signed and packaged the build as AAB/APK (and IPA for iOS), distributed to testers, submitted to the chosen distribution channel where required, then released the version matching the deployed API. Maintenance covers store privacy declarations, operating-system camera/permission changes, API compatibility, and collecting user feedback for iteration.

Outcome: a mobile companion that reduces a student's check-in to a single tap from a phone that is already in their hand, while keeping one authoritative attendance record shared with the web dashboard and the door-side reader.
